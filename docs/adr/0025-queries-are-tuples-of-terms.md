# ADR 0025 — A query is a tuple of terms, and a term may be optional

**Status:** Accepted · **Date:** 2026-08-02 · **Resolves:** Q17

## Context

Queries were hand-written methods, one per shape: `iter_pair`, `iter_triple`, `for_each_pair_mut`.
That worked and had two limits.

**No optional components.** A system wanting "every entity with a `Transform` and a `Sprite`, plus
its `SortOrder` if it has one" could not say so. So it asked for the required pair and then called
`world.get::<SortOrder>(entity)` per entity — which is exactly the per-entity lookup archetype
storage exists to avoid. The renderer was doing 40,000 of them per frame at 20,000 sprites, and after
ADR 0024 removed the component-id cost, this was what remained.

Optional is not an exotic case. *Requiring* a component means an entity silently vanishing from a
query when someone forgets to add it, which is a bad failure — so a well-written system treats most
of what it reads as optional. `render_quads` had the same shape for the same reason.

**And every new shape needed an engine change.** A game author who cannot express a query without
editing the engine is a real limit on invariant I5, and it applies to the agent as much as to Justin.

## What other engines do

**Bevy** defines a `QueryData` trait and implements it for `&T`, `&mut T`, `Option<&T>`, and for
tuples — up to 15 elements, generated by macro, because Rust has no variadic generics. `Query<(&A,
Option<&B>)>` works because `Option<&B>` is itself a `QueryData` implementation. It also caches which
archetypes a query matches in a `QueryState`, since "gathering archetypes is a costly operation".

**Flecs** makes the same structural point from the other direction: "a query can often match entire
archetypes instead of individual entities. This is one of the main reasons why queries in an
archetype ECS are fast."

That is the shape worth copying. The disagreement was only about how much machinery Amadeo should
take on to get it.

## Decision

**Justin chose the trait-plus-macro approach**, presented against two alternatives (hand-writing each
shape, or a lower-level per-archetype accessor) with the legibility cost stated up front.

A query is a tuple of terms implementing `QueryTerm`:

```rust
for (entity, (transform, sprite, order, global)) in
    world.query::<(&Transform, &Sprite, Option<&SortOrder>, Option<&GlobalTransform>)>()
{
    // ...
}
```

- `&T` — required. An archetype without it does not match.
- `Option<&T>` — optional. Never excludes anything; yields `None` where absent.
- Tuples up to eight terms, generated by one macro.

Each term resolves its column **once per archetype**, then the iterator walks rows. The per-entity
cost is an array index.

### This is the one deliberate piece of clever Rust in the ECS

`CLAUDE.md` §6 asks for boring Rust and this is a trait with an associated type plus a code-writing
macro. The exception is recorded here rather than left to be rediscovered, along with why the
machinery has the shape it does — all three points are in the module docs so they are next to the
code, not only in an ADR:

- **`Columns: Copy`** is what makes the row loop cheap. A term's per-archetype state is a slice, or
  an `Option` of one; both are `Copy`, so reading a row copies a fat pointer rather than re-borrowing.
- **The lifetime `'w` sits on the trait**, not on each method, because the borrowed slices have to
  outlive the loop that reads them.
- **The macro exists because Rust has no variadic generics.** Eight arities means eight identical
  implementations differing only in how many letters they mention. Writing them by hand would be the
  same code eight times, which is worse to read *and* worse to maintain.

### Read-only, deliberately

Mutation stays with the existing hand-written `for_each_mut`, `for_each_pair_mut`, and
`for_each_triple_mut`.

Handing out two `&mut` into one archetype requires proving they point at different columns. Those
methods do it with `slice::get_disjoint_mut`, which checks at runtime; a *generic* version cannot,
because the compiler does not know two type parameters are distinct types. Bevy solves this with
`unsafe`. This crate forbids `unsafe`, and the measured problem was entirely on the read side, so
the split is honest rather than a compromise.

## The measurements

Sprite collection at 20,000 sprites, release build, across the three changes that touched it:

| | Time | Share of a 60 Hz frame |
|---|---|---|
| First working batcher (string sort key) | 7.9 ms | 47% |
| Integer sort key, no trigonometry (ADR 0023) | 5.13 ms | 31% |
| Component ids as constants (ADR 0024) | 3.32 ms | 20% |
| **Optional-component query (this ADR)** | **2.58 ms** | **15.5%** |

Also 50,000 sprites on one tilesheet: 11.55 ms → **5.48 ms** across the same span.

**A correction to the earlier numbers is folded in here.** The benchmark fixture gave no entity a
`GlobalTransform`, so every sprite took the batcher's fallback path and rebuilt a matrix from Euler
angles — three `sin_cos` calls each. No real game is in that configuration, because every game
registers `propagate_transforms`. The fixture now inserts `GlobalTransform` and runs one propagation
pass, which is why the last row improves by more than the query change alone accounts for.

## Consequences

- **Any read query shape now works without an engine change**, including shapes nobody anticipated.
  That is invariant I5 applied to the ECS: the agent can express a query as freely as a human can.
- **`render_quads` and `collect_sprites` both lost their per-entity lookups**, and `render_quads`
  additionally lost the collect-into-a-`Vec`-then-resolve dance it needed because the old query
  borrow could not coexist with `world.get`.
- **`Archetype` is now `pub`**, with `#[doc(hidden)]` and every method still crate-private. It has to
  be nameable for `QueryTerm` to be a public trait; it is effectively sealed, since an outside
  implementation could not do anything with an `&Archetype`.
- **The old `iter_pair` and `iter_triple` still exist** and still work. Nothing was forced to migrate,
  and a test asserts the old and new paths see the same world — if they ever disagreed, one would be
  wrong and the renderer sits on both.
- **Iteration order is unchanged**: archetype order, then row order. Draw order and state hashes both
  depend on that being reproducible (invariant I3), and a test pins it.
- **Eight terms is the current ceiling.** Raising it is one more macro line. Bevy stops at 15 and
  suggests nesting tuples beyond that; the same works here.

## Rejected alternatives

**Keep hand-writing each shape.** Every method stays ten obvious lines with no traits, macros, or
lifetime puzzles — a real fit for a codebase whose author is still learning Rust. Rejected because
the count explodes once optional terms exist (required-or-optional across two to four components is
dozens of near-identical methods, each a place for an off-by-one), and more importantly because it
caps expressiveness: a shape nobody anticipated would need an engine change, which works against I5
for the agent as much as for Justin.

**A lower-level per-archetype accessor.** Expose archetype walking and let a system grab an optional
column itself. Solves the measured cost with far less machinery and stays concrete. Rejected because
it is a design nobody else uses, so there is no reference to check it against, and it pushes
iteration bookkeeping into every system — which is more places to get iteration order subtly wrong,
and iteration order feeds the state hash.

**Cache the matching archetypes, as Bevy's `QueryState` does.** A further optimisation on top of this
one. Deliberately not done: it needs invalidation when a new archetype appears, which is a
correctness risk, and the measurement says the remaining cost is no longer in finding archetypes.
Worth revisiting only against a number.
