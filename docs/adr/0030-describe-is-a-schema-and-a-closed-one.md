# ADR 0030 — `describe` is a schema, and a closed one

**Status:** Accepted · **Date:** 2026-08-03 · **Closes:** M1 exit gate 4 · **Amends:** ADR 0012, ADR 0027

## Context

M1 exit gate 4 said `describe` output should be sufficient to write a new component and system
without reading engine source. It was tested by doing it — `Trap` and `spring_traps`, shipped in the
Vault — and **the claim is false**. `docs/09-gate-4-describe-is-not-enough.md` is the write-up.

Five things were missing. The important realisation is that they are **two different kinds of
thing**, and treating them as one question is what made this look hard.

| Gap | Kind |
|---|---|
| 1. how to declare a component (`impl Component`, the derives) | API |
| 2. how to register one (`app.register_component::<T>()`) | API |
| 3. a system's signature (`fn(&mut World)`, stages, `.after`) | API |
| 4. how to query the world (`world.query::<(&A, &B)>()`) | API |
| 5. **resources are absent entirely** | **schema** |

Gap 5 is not "the manual is missing". `Run` holds the Vault's score and its win/lose state, it is
reflected, and `describe` simply did not emit it. That is `describe` failing at the job it already
claims. Looking at it properly turned up two more of the same kind, neither of which the gate had
noticed:

- **The schema was not closed.** `Run.phase` reports `"type": "Phase"`, and `Phase` is neither a
  component nor a resource, so nothing registered it and there was nowhere to look it up. The schema
  named types it could not describe — so nothing could know the legal values are `Playing`, `Won`,
  `Lost`.
- **A fixed array's length existed only inside its name.** `[f32; 2]` reflects as
  `TypeKind::List { element }` called `"array<f32, 2>"`. Anything needing the count — an editor
  deciding how many boxes to draw, a generator deciding how many numbers to emit — had to parse it
  back out of a string.

## What the research found

**Bevy's Remote Protocol is the closest analogue** — a Rust ECS engine with a reflection registry
exposing itself over JSON-RPC. Two things happened to it.

Resources were missing and were **added later** (`bevy/list_resources`, `bevy/get_resource`,
`bevy/insert_resource`). Same gap, same conclusion, reached independently.

And the schema alone turned out not to be enough to *make a call*. A third-party crate added a
`discover_format` method, its README saying `bevy/registry/schema` "doesn't show the actual JSON
format needed for BRP operations" — leaving people to reverse-engineer the shape out of error
messages.

**MCP** argues against the other candidate. Its servers may return an `instructions` string at
handshake describing how to use the server, and the specification is explicit that it is a hint for a
system prompt rather than a specification. Most servers do not set it. Prose inside a protocol reply
is a known pattern that stayed marginal.

## Decision

### 1. `describe` is a schema. Gaps 1–4 stay in the repo's documentation

**Invariant I5 is what settles this.** I5 says anything the editor can do, the CLI and RPC can do.
The editor will never declare a new Rust component type — that means editing the game crate and
recompiling. So "how do I write `impl Component`" is not a capability the editor has, and I5 does not
put it in the protocol's remit. **Gate 4 asked the protocol for something the project's own
invariants do not ask of it.**

The fallback is always available: ADR 0016 has the CLI *build and launch the game*, so anything
speaking this protocol has the repo checked out. "Read `docs/07`" cannot be unavailable.

`describe` carries a **`manual` key naming the file** — a pointer, not the prose. Prose copied into a
protocol reply is documentation nothing recompiles, so it drifts; a path does not. And saying nothing
would leave a reader to conclude the absence means impossible.

### 2. Resources are first-class

`describe` gains a `resources` section beside `components`. `ResourceSlot` gains `register_schema`,
and `World::register_resource_schemas` fills a registry in sorted name order.

### 3. The schema is closed: registering a type registers everything it names

`Reflect` gains a defaulted `register_dependencies(&mut TypeRegistry)`, generated by the derive —
one line per field type, per variant field type, per element type — and called by
`TypeRegistry::register`. Bevy does the same thing with `register_type_dependencies`.

The entry is inserted **before** recursing, so a self-referential type terminates instead of
overflowing the stack. That is a test, not a hope.

The closure lands in a third section, `types`, rather than in `components`. They answer different
questions: `components` is "what can I put on an entity", a closed list to pick from; `types` is
"what does this field's type mean", a lookup table. `Phase` in `components` would be a lie.

### 4. `TypeKind::List` carries a length

`Some(2)` for `[T; 2]`, `None` for `Vec<T>`. Omitted from the JSON when absent, matching how `unit`
and `range` already behave, so `"length" in kind` is a straight answer.

### 5. `describe.example` emits a working instance

Given a type, a **minimal valid instance** in both spellings — the scene block and the JSON — both
generated from one `Value`, so they cannot disagree. Numbers are zero, or a declared range's minimum
where zero would be outside it. An enum takes its first variant.

The point is the *shape*: that `translation` takes three numbers, that a list of pairs needs `- `
lines, that `phase` wants a bare word and **not** a quoted string. That last one is the clearest
justification for the whole feature — bare-versus-quoted is scene-format grammar rather than type
information, so no amount of schema would have taught it, and getting it wrong produces a file that
parses and then fails to load.

**The testable property is that the emitted example loads**, and that is the test: every component
the engine has, pasted into a scene, parsed, validated against the real registry, and instantiated.

`describe <Type>` now resolves against the whole schema rather than the components alone, so
`describe Run` and `describe Phase` both answer. Both used to be "no such component" — true, useless.

## Consequences

**Good:**

- The three structural gaps are closed and pinned by tests in the game that found them
  (`games/vault/tests/gate_four.rs`).
- The editor gets what it needs for a `Phase` dropdown and an `[f32; 2]` field, years before there is
  an editor. Both were unbuildable before, and neither would have been discovered until M4.
- `describe` is now honest about its own boundary rather than silently short of the gate.

**Bad, and accepted:**

- **Gate 4 stays formally unmet**, and the roadmap records it as tested-and-superseded rather than
  passed. That is the correct outcome for a gate that asked for the wrong thing.
- **The registry is bigger.** Registering `Transform` now also registers `f32`, `array<f32, 3>` and
  so on. That is the point, but it means `registry.names()` and `describe`'s `types` are no longer
  the same list, and three existing tests had to be updated to say so.
- **`describe` now needs a `World`**, because resources live there. Its signature changed and it
  returns a `Result` — a resource and a component sharing a name with different shapes has no honest
  document to emit.
- **The example is minimal, not realistic.** `Transform` comes back at the origin with zero scale,
  which is valid and invisible. It teaches spelling, not values.
- **A map has no scene form**, so `describe.example` omits the scene block for a type containing one
  and says why. That is ADR 0027's recorded gap surfacing rather than a new one.

## What was rejected

- **An `authoring` block inside `describe`** — the derives, the registration call, a system's
  signature, as prose in the reply. Makes the gate literally true and is small. Rejected because it
  is documentation that nothing recompiles: it drifts the first time the API changes, and MCP's
  equivalent field exists and stayed marginal for the same reason. A pointer costs one line and
  cannot go stale.
- **Leaving everything and recording the failure.** Zero work, and `docs/09` already states the
  finding — but it leaves resources genuinely missing from the schema, which is a hole in what
  `describe` already claims rather than a scope decision.
- **String-parsing `array<f32, N>` in the example generator** instead of adding `length`. Would have
  worked and would have left the next consumer to write the same parser.
- **Emitting `None` for an `Option` example.** Both are valid; `None` writes as a bare field name
  that the scene parser reads back as an empty list, so it is the one case an example cannot usefully
  show.
- **Registering resources through an explicit `register_resource` call**, mirroring components.
  Honest, and it would report resources that exist but have not been inserted yet. Rejected because
  it is a second call every game must remember, and forgetting it is exactly the failure ADR 0016
  found in `quad-demo`. Reading the live world means a resource inserted mid-run appears only once it
  exists, which is a real limitation and a smaller one.

## What this does *not* fix

**Gaps 1–4 are still gaps** — they have moved, not closed. An agent that has never seen this engine
still cannot write a system from the protocol alone, and `docs/07-working-with-the-code.md` is where
it has to look. If that ever becomes intolerable, the answer is a generated API surface rather than
prose in a reply, and it should supersede this ADR rather than amend it.

**The confound in `docs/09` is unaddressed.** The experiment was run by an agent that had already read
the engine source, so the gaps are ones it *noticed* rather than ones it was stopped by. The stronger
test — give the JSON to a reader with no prior exposure — has still not been run.
